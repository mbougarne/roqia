# Maintainer feasibility tools

These tools support the first 10 ordered tickets. They are not production download, prayer or media services. Results and open gates are in [the Android report](../../docs/feasibility/android/README.md).

## Requirements

Use the locked Yarn dependencies, Python 3.9+, curl with the system trust store, Node with tzdb 2026c or newer, and ffprobe for real audio metadata. Android builds here use JDK 21, the installed Android SDK and the existing debug signing key. `yarn install --frozen-lockfile` installs exact tested dependencies from yarn.lock.

```sh
yarn feasibility:test
yarn feasibility:inventory
yarn feasibility:prayer
python3 tools/feasibility/content.py acquire
python3 tools/feasibility/content.py package-hafs
python3 tools/feasibility/content.py validate
python3 tools/feasibility/recordings.py --fetch-samples
```

Acquisition and generated packs go to `.roqia-feasibility/`, which is ignored. `package-hafs` refuses to overwrite an existing version. A changed upstream download fails its source lock; investigate and version the source instead of silently accepting it. Never normalize or replace characters in canonical Quran text. Source locks are independent of generated manifests.

`recordings.py` without `--fetch-samples` is deterministic and offline. With that flag it fetches six public MP3s and records transport hashes/decoder metadata, not religious approval. Full provider snapshots are fixtures with retrieval URLs/hashes in the report. No provider credential is needed or included.

For catalog export, copy `review.template.json` outside the repository, fill it only after actual review, and bind it to the generated manifest SHA-256. Then run:

```sh
python3 tools/feasibility/content.py catalog --pack /absolute/path/to/reviewed-pack --review /absolute/path/to/review.json --base-url https://your-approved-static-host/immutable-version/
```

This prints catalog JSON; it does not upload or prove host availability. No real host or ready seed is configured by this PR. Keep a pack draft until source, canonical text, font and offline rendering review all pass. A manifest or file change invalidates the review.

## Android probes

Use only the intended emulator serial, especially when another Android device is connected. Back up relevant local app data outside Git before an upgrade. Do not uninstall or clear data to work around a signature mismatch.

```sh
export JAVA_HOME=/path/to/jdk21
export ANDROID_HOME=/path/to/android/sdk
cd android
./gradlew :app:assembleDebug -PreactNativeArchitectures=arm64-v8a
cd ..
adb -s emulator-5554 install -r android/app/build/outputs/apk/debug/app-debug.apk
adb -s emulator-5554 reverse tcp:8081 tcp:8081
adb -s emulator-5554 reverse tcp:8082 tcp:8082
```

Run `yarn start --port 8081` and `yarn feasibility:serve` in separate terminals. The fixture server listens only on 127.0.0.1:8082 and serves deterministic generated bytes, not filesystem contents. Then:

```sh
python3 tools/feasibility/run-android-probe.py stable --serial emulator-5554
```

Available scenarios: `stable`, `range200`, `changed`, `wrong206`, `range416`, `unknown`, `recovery`, `reattach`, `provider`, `audio`, `alarm`, `timezone`, `cleanup`. Supply `--adb /absolute/path/to/adb` if needed. The runner refuses a non-emulator serial and creates a fresh debug activity task without clearing app data. After editing the probe code, restart the debug app process once so results use the current Metro bundle; do not do this during a recovery test.

The `changed` and `wrong206` scenarios succeed only when corruption is rejected; `range416` succeeds on native failure. `provider` uses the pinned sample in the evidence inventory and fails if the remote bytes change. The native file adapter only touches names under the app's `files/feasibility` directory.

For recovery, run `recovery`, background the app, terminate only its process with `run-as ... kill -9 <verified-app-pid>`, and run `reattach`. This tests a persisted paused job; it is not a force-stop or active-transfer survival claim. Never kill a guessed PID.

For `audio --background`, the runner brings the existing activity back after 28 seconds so the JavaScript observer can finish. Native playback continues while backgrounded; the observer's timer is not a reliable sleep deadline. Android `cmd media_session dispatch pause` and `play` can exercise the remote service. Stop the test afterwards with `cleanup`.

`alarm` schedules 8 seconds ahead. A finished JS scenario means **armed**, not delivered. Inspect native `alarm-delivered`, `alarm-media-started`, `alarm-media-completed` and `alarm-service-stopped` events. Exact access must be enabled explicitly on the test device; denied access is a real failure result. To test idle, background/lock the emulator, use `dumpsys deviceidle force-idle`, and always restore with `dumpsys deviceidle unforce`. Restore any test-only permission changes. Closely spaced idle alarms may be throttled by Android.

The journal is in `files/feasibility/events.jsonl`, readable through `adb -s emulator-5554 exec-out run-as name.roqia.app cat files/feasibility/events.jsonl`. It contains probe events, not user counters. Do not commit device backups, release credentials, arbitrary Logcat dumps or downloaded corpora. Retain only scoped test evidence. `timezone` may finish successfully as a probe while reporting `supported: false`; that result blocks prayer integration.

## Review boundaries

The debug activity, synthetic tone and native probe classes live in the debug source set. The JS component is registered only for Android development builds. Native downloader dependencies still contribute release services/permissions; inspect the merged release manifest before shipping. The normal screens, existing data IDs, notification schedules and released version number are unchanged.
